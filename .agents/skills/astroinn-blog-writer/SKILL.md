# Astroinn 博客写作

在当前仓库的 `_posts/` 中工作。先理解用户本次要新写、整理记录，还是润色已有文章；尊重用户指定的主题、日期、范围和发布状态。需要把对话或资料写成文章时，先读取原始记录，再提炼可核实的事实。

## 写作与润色

- 默认使用简体中文，语气直接、清楚，保留作者的第一人称经历和具体技术细节。润色时保留原意、命令、代码、链接和已确认的结论；不为追求流畅而添加未经证实的原因。
- 技术排障文章优先交代环境与现象、按时间或因果顺序展示排查证据、说明实际解决方法和验证结果。区分日志直接显示的事实、根据事实作出的判断，以及尚未验证的猜测。其他主题按内容选择结构。
- 对可能变化或不确定的技术事实，查阅适用的官方文档或原始资料，并在文章中给需要来源支撑的结论添加直接链接。不要编造日志、运行结果、时间、引用或个人经历。
- 发布前留意文章中的账号、邮箱、内网地址、设备信息和密码示例。保留用户明确要公开的内容；对意图不明且可能敏感的内容，先把具体位置和风险说明清楚。

## Chirpy 文章格式

- 新文章放在 `_posts/YYYY-MM-DD-英文短名.md`。文件名日期与 front matter 的 `date` 日期一致；遵循用户指定的日期和时区，未指定时使用当前 Asia/Shanghai 日期与时间。
- front matter 至少包含 `title`、`date`、`categories` 和 `tags`。优先沿用仓库现有分类；分类最多两级，英文标签用小写。按需加 `description`、`image` 等字段，不机械复制示例文章。
- 标题准确描述文章主题；摘要用一两句话交代场景与读者能得到的内容。正文中的相对路径、图片和代码块遵循本仓库已有用法。需要特定 Chirpy 语法时，查阅 [官方写作指南](https://chirpy.cotes.page/posts/write-a-new-post/)。

## 正文排版

仓库中的 [《文本与排版演示》](../../../_posts/2022-05-02-文本与排版.md) 展示了当前主题的实际写法。写作或润色时，按内容选用其中的格式，不把演示文章的全部组件套进正文。

- 文章已有 front matter `title` 时，正文通常从简短引言或 `##` 小节开始，避免再重复同名 `#` 标题。按内容层级使用 `##`、`###`；标题、段落、列表和代码块之间留空行，让扫描和阅读都顺畅。
- 命令、配置、日志分别使用带语言标记的围栏代码块，如 `bash`、`yaml`、`nginx`、`text`；需要交代文件来源时，可参考演示文章在代码块后使用 `{: file='路径'}`。代码和输出分开呈现，不把推测写进原始日志。
- 只有确实需要提醒读者的补充信息才用提示块。沿用演示文章的写法：引用块下一行接 `{: .prompt-tip }`、`{: .prompt-info }`、`{: .prompt-warning }` 或 `{: .prompt-danger }`；普通解释保留为正文，避免提示块过多。
- 图片沿用仓库现有资源路径；需要尺寸、对齐、说明文字或深浅色模式时，参考演示文章的图片属性写法。对流程确有帮助时再用表格或 Mermaid 图；使用数学公式或 Mermaid 时，按主题需要在 front matter 中启用 `math: true` 或 `mermaid: true`。
- 文件路径可按演示文章使用 `` `路径`{: .filepath} ``，引用来源或补充说明可用链接、脚注。只在这些样式能帮助读者理解时使用，不为排版而增加装饰。

## 完成工作

- 若用户只要草稿、润色或本地修改，只编辑请求涉及的 Markdown，不提交或推送。若用户明确要求发布，再按仓库现有流程提交、推送并核对 GitHub Pages 构建结果。
- 对编辑过的文章检查 front matter、文件名日期、代码块和明显的格式问题。能运行构建时按任务需要验证；不能运行时如实说明。最终简要报告改了什么、文章位置，以及是否已发布。
